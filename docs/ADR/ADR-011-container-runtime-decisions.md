# ADR-011: Container Runtime Decisions (Production Docker Images & Compose Topology)

- **Status**: Approved & frozen (Phase 10 Stage 10.3)
- **Date**: 2026-08-18
- **Related Freeze**: `docs/ECR/PHASE10/ECR-Phase10-0001/ECR-Phase10-0001.md` §20.2; Stage 10.3 Implementation Plan

## Context

Phase 10 Stage 10.3 introduces production-grade Docker images and Docker Compose topology for the AIOS API and Web applications. The repository already had Dockerfiles and compose configuration, but they contained a critical entrypoint defect (`dist/server.js` instead of `dist/main.js`), insecure defaults (`TBIT_API_KEY=changeme`), missing security headers, and lacked evidence-based justification for base image and UID choices. Stage 10.3 corrects these defects and documents all decisions with repository evidence.

## Problem

What are the evidence-based decisions for:
1. Base image selection for API and Web containers?
2. Non-root user UID/GID choices?
3. Entrypoint correction for API container?
4. Healthcheck strategy (readiness vs liveness)?
5. Secret handling in compose?
6. CSP policy for Three.js/WebGL compatibility?
7. Volume permissions for T-Bit vault persistence?

## Decision

### 1. Base Images

| Container | Base Image | Evidence |
|-----------|------------|----------|
| API (builder + runner) | `node:22-alpine` | Existing Dockerfile uses it; `pnpm build` passes 11/11; `@muf/tbit-core` builds successfully on musl libc; no native module failures in CI; Node.js 22 is LTS |
| Web (builder) | `node:22-alpine` | Same as API builder; Vite/TypeScript build passes |
| Web (runner) | `nginx:alpine` | Existing Dockerfile uses it; serves static files efficiently; minimal attack surface |

**Rationale**: Alpine-based images reduce attack surface and image size. Node.js 22 on musl libc is validated by the existing successful build pipeline (11/11 tasks). No evidence of native module incompatibility with `@muf/tbit-core` or other workspace packages.

### 2. Non-Root User UID/GID

| Container | User | UID | GID | Evidence |
|-----------|------|-----|-----|----------|
| API | `nodejs` | 1001 | 1001 | Existing Dockerfile creates `adduser -u 1001`; avoids conflict with common host UID 1000; verified by `docker run --rm aios-api id -u` → `1001` |
| Web (nginx) | `nginx` (default) | 101 | 101 | `nginx:alpine` default user; no custom user needed; runs as non-root by default |

**Rationale**: UID 1001 avoids collision with host user (typically 1000). The existing Dockerfile already established this pattern. nginx default UID 101 is standard and requires no modification.

### 3. API Entrypoint Correction

**Defect**: `apps/api/Dockerfile` used `CMD ["node", "dist/server.js"]` — this module only exports `createServer()` and `startServer(app)` but does **not** start the HTTP listener.

**Correction**: `CMD ["dumb-init", "node", "dist/main.js"]` — `dist/main.js` imports and calls `createServer()` then `startServer(app)`, which binds to `0.0.0.0:3001`.

**Evidence**: 
- `apps/api/src/main.ts` → compiles to `dist/main.js` → calls `startServer(app)`
- `apps/api/src/server.ts` exports `startServer(app)` which calls `app.listen()`
- `apps/api/package.json` `"start": "node --env-file=../../.env dist/main.js"` (dev entrypoint)
- Compiled output verified: `dist/main.js` exists and contains the startup logic

### 4. Healthcheck Strategy

| Probe | Endpoint | Purpose | Compose Usage |
|-------|----------|---------|---------------|
| Liveness | `GET /livez` | Process alive (always 200 if Node running) | Documented for K8s; not used in Compose v2 (single healthcheck) |
| Readiness | `GET /readyz` | Vault initialized + secrets present | `healthcheck.test: ["CMD", "wget", "-q", "--spider", "http://localhost:3001/readyz"]` |
| Web | `GET /health` | Nginx serving | `healthcheck.test: ["CMD", "wget", "-q", "--spider", "http://localhost/health"]` |

**Rationale**: Stage 10.2 implemented `/livez` (liveness) and `/readyz` (readiness) endpoints. Compose `depends_on: condition: service_healthy` should gate on readiness, not liveness. `/readyz` returns 503 until vault is initialized, ensuring web only starts when API is fully operational.
### 5. Secret Handling

**Decision**: Remove `TBIT_API_KEY=changeme` default from `docker-compose.yml`. Require explicit value via `.env` file generated by `pnpm run setup:secret` (which writes to repository-root `.env`).

**Evidence**: 
- `.env.example` documents: "The real values are generated automatically by: `pnpm run setup:secret`"
- `scripts/setup-tbit-secret.mjs` generates `TBIT_API_KEY` and `VITE_TBIT_API_KEY` identically
- Current compose default `changeme` is a security anti-pattern

### 6. CSP Policy for Three.js/WebGL

**Policy**:
```
Content-Security-Policy: default-src 'self'; 
  script-src 'self' 'unsafe-inline' 'unsafe-eval'; 
  style-src 'self' 'unsafe-inline'; 
  img-src 'self' data: https:; 
  font-src 'self' data:; 
  connect-src 'self' http://api:3001; 
  frame-ancestors 'self'; 
  base-uri 'self'; 
  form-action 'self';
```

**Justification for `unsafe-eval`**: Three.js compiles GLSL shaders at runtime using `new Function()` / `eval()`, which requires `'unsafe-eval'` in `script-src`. This is a known Three.js requirement. The risk is mitigated by:
- Restricting `connect-src` to API only
- `'self'` for all other directives
- No external script sources allowed

**Evidence**: Web app uses `@react-three/fiber` and `@react-three/drei` (Three.js ecosystem), which require runtime shader compilation.

### 7. Volume Permissions for T-Bit Persistence

**Decision**: 
- API Dockerfile creates `/data` with `chown -R nodejs:nodejs /data`
- `TBIT_VAULT_ROOT=/data/spaces` (subdirectory created by T-Bit at runtime)
- Compose mounts named volume `tbit-data:/data`
- Volume ownership preserved by UID 1001 in container

**Evidence**: 
- `apps/api/.env.example`: `TBIT_VAULT_ROOT=/data/spaces`
- Existing Dockerfile: `RUN mkdir -p /data && chown -R nodejs:nodejs /data`
- T-Bit vault initialization creates `spaces/` subdirectory

### 8. Signal Handling

**Decision**: Add `dumb-init` as PID 1 in API container (`apk add dumb-init` in runner stage, `CMD ["dumb-init", "node", "dist/main.js"]`).

**Rationale**: Node.js as PID 1 does not reap zombie children or forward signals properly. `dumb-init` (12KB) solves this. Alpine package available.

### 9. Production Image Minimization

**API Runner**: Copy only `dist/` + production `node_modules` (from `pnpm install --prod`). Do **not** copy `packages/` source.

**Web Builder**: Copy only `apps/web` + required workspace config. Do **not** copy all `packages/`.

**Rationale**: Reduces image size and attack surface. Verified by `docker build` and runtime smoke tests.

## Consequences

### Positive
- ✅ API container starts correctly (entrypoint fixed)
- ✅ Non-root execution validated (UID 1001 / 101)
- ✅ Readiness-gated dependency ordering (web waits for API ready)
- ✅ No insecure secret defaults
- ✅ Security headers on both API (helmet) and Web (nginx CSP)
- ✅ T-Bit vault persistence via named volume with correct permissions
- ✅ Evidence-based decisions documented for audit

### Negative / Risks
- ⚠️ CSP `unsafe-eval` required for Three.js — mitigated by restrictive other directives
- ⚠️ `/readyz` returns 503 until vault initialized — operator must call `/api/v1/tbit/vault/init` (expected behavior)
- ⚠️ CI/CD must inject real `TBIT_API_KEY` via `.env` — documented in `.env.example`
- ⚠️ Image size targets not mandated by ECR — monitor but don't block

## Alternatives Considered

| Alternative | Rejected Because |
|-------------|------------------|
| `node:22-slim` (Debian) | Larger attack surface; musl validated; no benefit |
| UID 1000 (match host) | Container escape risk if volume mounted; 1001 avoids collision |
| Custom nginx user | Default `nginx` user (101) works; no need to modify |
| `/health` for compose healthcheck | Returns 200 even when vault not ready; breaks readiness gating |
| Keep `TBIT_API_KEY=changeme` | Security anti-pattern; violates secret management policy |
| Distroless base images | Added complexity; Alpine already minimal and validated |
| Remove `unsafe-eval` from CSP | Breaks Three.js/WebGL rendering; core product functionality |
